# Независимые кодовые заготовки для сборки бота

**Не production и не выполнение T-101/T-104/T-201.** Это самостоятельные, полностью локальные и тестируемые внутренние функции. Они не вызывают YCLIENTS, Telegram, сеть, БД и не читают секреты.

## Что внутри

- models.py — внутренние нормализованные DTO, **не формат API YCLIENTS**.
- records.py — детерминированный diff для появления, переноса и явной отмены записей.
- occupancy.py — занятость залов по колонкам аренды и ресурсам групповых событий, цена и свободные слоты.
- access.py — минимальный default-deny RBAC с проверкой принадлежности записей.
- phones.py — чистая нормализация телефона и разрешение неоднозначных совпадений.
- marketing.py — opt-in сегментация новостных рассылок.
- windows.py — стабильные пустые окна из 8 последовательных недель.
- tests/test_scaffold_domain.py и tests/test_scaffold_extra.py — 21 синтетический тест без токенов и реальных данных.

Запуск из корня репозитория:

    python -m unittest discover -s tests -p 'test_scaffold_*.py'

## Как собирать

1. T-101: утвердить реальные типы app/domain, настройки и инфраструктуру.
2. T-103: подтвердить YCLIENTS API и внутренний маппинг response -> Record/Activity/Hall. Без verified нет сетевого адаптера.
3. T-104: перенести records.py и occupancy.py в app/domain, тестировать на обезличенных fixtures и дополнить жизненный цикл: окно [-1;+14], record.get для пропавших записей, week-based empty_windows, обработка времени/ресурсов.
4. T-201: перенести access.py, завершить матрицу разрешений для каждого действия/кнопки и обеспечить проверку в сервисах.
5. T-301: интегрировать phones.py с безопасной привязкой по contact.user_id, реализовать R4 и очистку номера после успеха.
6. T-305: использовать marketing.py только для анонсов с opt-in; служебная рассылка должна проверять состав конкретного занятия.
7. T-403: интегрировать windows.py после полной синхронизации данных восьми недель из API, связать расчёт с актуальным studio.yaml.
8. Получить независимое ревью по docs/REVIEW.md; только владелец разрешает merge.

## Предостережения

- diff **не** считает пропавшую из API запись отменой: недостаточно информации без record.get/fallback (ADR-04).
- occupancy работает **только с нормализованными внутренними** записями; несовпадение ресурсов или отсутствие ID не означает свободный зал.
- RBAC — стартовая часть матрицы, не полная система авторизации. schedule.view не означает доступа к персональным данным.
- Все вычисления времени получают явные aware datetime, время студии Europe/Moscow.
- Диспетчер, Runner и GPT-ревьюер здесь не разрабатываются (ADR-23).

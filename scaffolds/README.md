# Независимые кодовые заготовки для сборки бота

**Не production, не закрывает задачи T-101/T-104/T-201/T-301/T-305/T-403.** Это только внутренние чистые функции, не реальные ответы API YCLIENTS. Ветка PR #1 остаётся draft до ревью.

## Модули

- `models.py`: внутренние нормализованные типы `Record`, `Hall`, `Activity`, `Interval`, `OccupancyResult`; не копировать как внешнюю схему API.
- `records.py`: `diff(previous, current, occurrence=...)`; фиксирует создание, отмену, перенос времени/зала/преподавателя/услуги.
- `occupancy.py`: `occupancy(..., records_complete=True, activities_complete=True)` после проверки полноты через адаптер; `free_slots` работает только с проверенным `OccupancyResult`, `price` использует явную студийную `ZoneInfo`.
- `windows.py`: 8 последовательных недель с `complete=True` и проверенным маппингом зала; параметры/цены брать из `studio.yaml`.
- `access.py`: начальная таблица RBAC. Арендатор видит только собственную запись типа `rental`, преподаватель — свою запись типа `class`. `Target` сервис должен построить из доверенной записи, **не** из Telegram callback.
- `phones.py`: нормализация и 0/1/несколько совпадений, некорректные кандидаты пропускаются, введённый номер проверяется; роль арендатора подтверждает T-301 по истории аренды.
- `marketing.py`: opt-in сегментация **анонсов**, исключает заблокировавших бота; служебные рассылки — отдельный сценарий.

## Команды проверки

```bash
python -m unittest discover -s tests -p 'test_scaffold_*.py' -v
```

Тесты намеренно без сети и реальных персональных данных. `make check` появится в T-101.

## Критичные интеграционные контракты

1. **Occurrence** — не выдуманное поле YCLIENTS. Это положительный *локальный* устойчивый номер транзакции изменения снимков. T-104 обязан сохранять его вместе со снимком, событиями и outbox в одной БД-транзакции; при повторе использовать тот же номер. После подтверждённого следующего изменения номер увеличивается. Без атомарной связи с БД возможны пропуски/повторы.
2. **Complete** — не догадка по числу недель или пустому HTTP-ответу. T-103/T-104 должны подтвердить полноту страниц API, всех временных окон, проверенный source/fallback для групповых событий и всех соответствий залов. Только тогда разрешено `records_complete`, `activities_complete`, `Hall.mapping_verified` и `HistoricalWeek.complete`. Если данных недостаточно — останавливать выдачу свободных окон/рассылку R6, эскалировать.
3. **RBAC** — `Target.record_kind` должен происходить из доверенной нормализации подтверждённых данных YCLIENTS. Не принимать это поле от клиента. Полная матрица прав и её применение в сервисах — T-201.
4. **Timezone** — `studio_timezone=ZoneInfo(settings.studio.timezone)`; другие временные метки приводятся к ней перед тарифом.
5. **Fixtures и API** — сопоставление внешних полей и классификация rental/class только после T-103. Кандидаты из API_MATRIX не равны проверенным путям.

## Порядок работы агентов

T-101 фиксирует DTO/миграции/Makefile. T-103 проверяет внешний API; T-104 интегрирует события/занятость и транзакционную последовательность, T-201 — права, T-301 — телефоны, T-305 — рассылки, T-403 — историю и окна. Выполнения этих задач не подразумеваются наличием scaffold. Сверить `PLAN.md` и `docs/REVIEW.md`, независимое ревью [R], merge только владелец.

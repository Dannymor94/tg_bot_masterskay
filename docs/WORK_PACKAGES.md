# WORK_PACKAGES — параллельная сборка Telegram-бота

Только `PLAN.md` определяет реальные статусы и зависимости. Оркестратор вне репозитория; пока агенты запускаются вручную. Использовать отдельные git worktree и ветки на каждую задачу.

| Волна | Что можно вести параллельно | Приёмка / ограничения |
|---|---|---|
| 0 | T-001 (человек), T-101 (каркас) | Миграции, `make check`, валидация настроек; ни одного реального YCLIENTS вызова агентом |
| 1 | T-102 (только YCLIENTS адаптер), T-105 (outbox/scheduler) | После T-101; две непересекающиеся ветки; оба [R] |
| 2 | T-103 (обезличенный spike, HUMAN запускает), T-201 (RBAC) | T-103 после T-001+T-102; T-201 после T-105 |
| 3 | T-104 (синхронизация/занятость), T-203 (очередь задач) | После собственных зависимостей; unit-тесты и ревью |
| 4 | T-301/T-302/T-303/T-304/T-305 и T-401/T-402/T-403 | Запускать только по зависимостям в PLAN; избегать общих файлов |
| 5 | T-204, T-205, T-404 — VPS и пилоты | Только человек разрешает merge и deploy |

## Готовые куски для сборки

`scaffolds/` — независимый **справочный код**, а не приложение и не автоматически принятые задачи. Перед переносом агент должен сверить инварианты `PLAN.md`, `docs/DECISIONS.md`, `docs/CONTRACTS.md` и провести тесты. Нормализованные DTO из примеров — внутренние структуры, не поля ответа YCLIENTS. При конфликте выигрывают утверждённые ADR и реальные fixtures, а не заготовка.

## Минимум участия владельца

В каждой issue агент получает **полный автономный цикл**: проверка зависимостей → fetch → собственный worktree и task-ветка → установка зависимостей → реализация и тесты → `make check` → commit/push → создание draft PR → передача независимому QA → самостоятельное исправление замечаний в том же PR. QA использует отдельное чистое окружение и публикует фактические результаты. Не требовать от владельца обычных команд терминала.

**Границы:** merge, deploy, утверждение ADR и использование реальных секретов, `make spike` и `make invite` остаются за владельцем. Внешний агент-диспетчер ещё не реализован (ADR-23), поэтому GitHub issue сама по себе не запускает локальный Claude Code; владелец запускает агента одним поручением, остальное делает агент. Если выполнение заблокировано средой, агент сообщает точный BLOCKED, а не требует рутинных действий без попытки самостоятельного разрешённого обходного пути.

## Правило интеграции

Не выполнять параллельное редактирование `PLAN.md` и общих контрактных файлов в одном рабочем дереве. Задачи завершаются в собственных ветках: после зелёного `make check` каждый агент сам делает commit и обычный `git push -u origin HEAD` из **своего** task-worktree, сообщает абсолютный путь, ветку, полный SHA и ссылку. До push и создания draft PR не считать задачу переданной на ревью. Затем независимое ревью `[R]` по точному SHA с реальным `make check`; REQUEST_CHANGES исправляет исполнитель с повторным push в тот же PR. Запрещены force push и push в `main`. Разрешение конфликтов и merge — владелец/уполномоченный им интегратор, не диспетчер.

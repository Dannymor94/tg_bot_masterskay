# T-105 — отчёт для независимого ревью [R]

Статус: реализовано, независимое ревью не проведено. Merge выполняет владелец.
База: `f8dcdea` (`origin/t-101-foundation`). Ветка: `t-105-outbox-scheduler`.
Текущий worktree первоначально стоял на baseline `05f1909`; новая ветка создана
от имеющегося локально T-101, без fetch, merge, push или изменения других worktree.
Полный diff: `git diff f8dcdea...HEAD`. Задача разделена на T-105a/b/c по лимиту diff.

Сделано:

- `enqueue(connection, OutboxDraft, cfg, now)` работает в транзакции вызывающего
  сервиса: UNIQUE защищает повтор, несовпадение получателя/kind/payload по тому же
  ключу вызывает ошибку. `next_attempt_at` — изменяемое время доставки, не часть
  идентичности сообщения. Задача/событие и outbox откатываются вместе.
- Тихие часы вычисляются чистой функцией в Europe/Moscow. Ночные события
  администраторам (`kind` из `admin_instant_events`) сохраняются в `summary`;
  обычные сообщения откладываются. Sender не отправляет `summary`.
  T-202 должен прочитать эти строки и включить их в сводку своей транзакцией.
- Sender использует `BEGIN IMMEDIATE` до чтения очереди и держит блокировку
  записи SQLite до фиксации результата ограниченного по времени запроса.
  Конкурирующий sender не может одновременно отправить ту же строку.
- 429: сохраняются attempts, next_attempt_at и общий cooldown в kv. Задержка
  равна максимуму Retry-After и экспоненциального backoff, считается от ответа.
  Сетевые ошибки/таймауты/5xx повторяются с ограниченным backoff; 400 и неверный
  payload переходят в failed. 403 сохраняет users.blocked_at и блокирует также
  остальные pending/summary получателя. Новые сообщения ему сразу blocked.
- Состояния доставки: pending, sent, failed, blocked, summary. Повторы сетевых
  ошибок не ограничены числом попыток, интервал ограничен конфигурацией.
  Глобальное ограничение частоты и cooldown сохраняются после рестарта.
- `run_period` атомарно фиксирует `scheduled:<job>:<period>` и DB-эффекты callback.
  Callback получает ту же connection, не должен отправлять сообщения/делать IO
  вне БД, открывать отдельную транзакцию или самостоятельно выполнять commit.
  Ошибка/отмена откатывает ключ и эффекты, позволяя повторить запуск.
- `Job` определяет последний наступивший ежедневный/еженедельный период по
  московскому календарю; при простое запускается только последний период,
  без перебора всех пропущенных. До времени сегодняшнего запуска это предыдущий
  наступивший период. Callback получает now; при построении эффектов для периода
  использует тот же `Job.period(now, timezone)` и устойчивые dedupe_key.
- Рабочий цикл запускается вместе с heartbeat, завершается по существующим
  сигналам. Новые бизнес-задания подключаются через список Job в run_jobs;
  список пока пуст: сводки и напоминания реализуются последующими задачами.
  Telegram вызывается только sender через aiogram; поддержаны текст и file_id фото.

Файлы: `app/domain/delivery.py`, `app/services/outbox.py`, `app/jobs/{outbox,
 scheduler,runner}.py`, `app/{runtime,__main__,settings}.py`, `app/config/studio.yaml`,
`tests/integration/test_{delivery,enqueue,scheduler}.py`,
`tests/unit/test_delivery_policy.py`, `PLAN.md`, этот отчёт.
Модели SQLAlchemy, DTO, миграция, адаптер YCLIENTS и CONTRACTS не изменены.
Новых зависимостей нет. Значения доставки добавлены в studio.yaml (version 2).
Инфраструктурные функции не являются пользовательскими действиями RBAC;
`can()` и проверки прав вызывающих пользовательских сервисов относятся к T-201.

Проверка: `make check` — passed, 69 тестов; ruff format, ruff check, pyright зелёные.
Новые сценарии: конкурентная постановка и отправка через разные engine,
конфликт dedupe_key, атомарность с задачей, пересоздание engine после сохранения
очереди/доставки/ошибки, 429 и cooldown другого получателя, ограничение частоты,
403 и последующие сообщения, 400, сеть, 5xx, timeout, отмена во время отправки,
сохранение ночных событий, календарные границы, ограниченный backoff,
конкурентные плановые запуски, rollback callback, следующий период,
остановка рабочего цикла. Тесты синтетические: без сети и ожидания реального времени.

Ограничение гарантии: атомарность SQLite не распространяется на Telegram.
Если Telegram принял сообщение, а процесс/соединение оборвалось до commit sent,
повтор возможен. Выбрана доставка с повторными попытками, без потери pending.
Тест `test_crash_rolls_back_and_exposes_remote_acceptance_window` явно показывает
это окно, включая возможный дубль. Обычный рестарт после commit sent не дублирует;
сбой до отправки не теряет сообщение. Абсолютная exactly-once доставка при таком
аварийном окне не заявляется. Реальные токены, сеть и VPS не проверялись.
SQLite write lock удерживается на время запроса (по умолчанию до 3 секунд).

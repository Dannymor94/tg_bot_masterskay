# T-103 — безопасная проверка прав YCLIENTS для блокера `records.list → 403`

**Связанные задачи:** [#37](https://github.com/Dannymor94/tg_bot_masterskay/issues/37) — owner-only реальная проверка, [#66](https://github.com/Dannymor94/tg_bot_masterskay/issues/66) — подготовка этого документа, [#64](https://github.com/Dannymor94/tg_bot_masterskay/issues/64) — отдельная задача по коду/матрице.
**Дата:** 2026-11-15. **Статус:** чек-лист готов; **права не проверены**, причина `403` не установлена.

## Границы проверки

- Это **осмотр настроек в интерфейсе**, который проводит владелец в своей уже авторизованной сессии YCLIENTS. Никаких новых HTTP/API-запросов к YCLIENTS, запусков `make spike`, `curl`, `httpx`, бота или Telegram.
- Токены уже хранятся в приватном файле вне репозитория, но сам факт наличия токенов **не подтверждает** их применимость к выбранному филиалу или операции. Не открывать/проверять значения токенов, `secrets.env`, переменные окружения, логи, HTTP-заголовки или тело ответа.
- Не отправлять номера филиалов, имена аккаунтов, телефоны, имена клиентов, записи, скриншоты или секреты агентам, в GitHub, чат и CI.
- **Не менять** роли, доступы, scopes, тариф, настройки филиала или приложение в рамках проверки. Если обнаружено недостаточное право — фиксировать результат и отдельно согласовывать минимально необходимое изменение. Права на создание/редактирование/удаление записей не требуются для цели этого расследования.
- Если раздел недоступен, имеет другое название либо его право невозможно подтвердить без приватных данных, фиксировать **`unknown`**, а не угадывать.

## Как выполнить UI-проверку (владелец)

1. **Правильный филиал.** Откройте в своей сессии YCLIENTS филиал студии «Мастерская». Локально, не копируя значение, сопоставьте его с тем филиалом, для которого настроен `company_id`. Успех `company.get` в прежнем spike **не доказывал совпадение филиала**. Результат: `BRANCH_MATCH=yes/no/unknown`.

2. **Системный пользователь и филиал.** В кабинете разработчика откройте своё приложение и раздел **«Доступ к API»**, не открывая значение токена. По [официальной инструкции YCLIENTS](https://support.yclients.ru/67-68-199--dostup-k-api/) системный пользователь создаётся автоматически, **но не добавляется в филиал, если ему не назначены права**; выбранные для приложения права действуют после подключения приложения. Приватно проверьте, что приложение подключено именно к целевому филиалу и системный пользователь получил там доступ. При необходимости дополнительно проверьте видимость доступа в **«Настройки → Настройки записи → Сотрудники»** или **«Лицензия → Управление сотрудниками»**. Не путайте системного пользователя интеграции с обычным сотрудником, оказывающим услуги. Не копируйте User token. Если связь приложения с филиалом/пользователем не подтверждена — `unknown`. Результат: `SYSTEM_USER_IN_BRANCH=yes/no/unknown`.

3. **Право читать журнал.** В той же карточке сотрудника с доступом откройте его **роль в колонке «Доступ» → «Права доступа» → «Журнал записей»**. Убедитесь, что блок просмотра доступен; отдельно проверьте два пункта:
   - **«Просматривать расписание и записи должностей»** — какие должности включены;
   - **«Просматривать расписание и записи сотрудников»** — какие сотрудники включены.

   Также учтите ограничение **«Ограничить доступ к истории расписания и записей»**: запрет на прошлые периоды может объяснить отсутствие данных за конкретную дату, но сам по себе **не доказывает причину API `403`**. Обратите внимание: YCLIENTS отдельно настраивает блок **«Окно записи»**; доступ к окну не заменяет право видеть журнал. Для `JOURNAL_SCOPE` укажите:
   - `all` — подтверждено чтение расписания и записей всех нужных сотрудников и должностей филиала за проверяемый период;
   - `own` — ограничение буквально собственными записями;
   - `none` — доступ к журналу отсутствует;
   - `unknown` — частичный набор чужих сотрудников, неизвестный период, недоступная страница или другие неоднозначные условия.

4. **Права приложения (partner).** В кабинете разработчика откройте карточку своего приложения и настройку **«Доступ к API»**: [YCLIENTS описывает](https://support.yclients.ru/67-68-199--dostup-k-api/), что здесь отмечают права системного пользователя приложения, которые действуют после подключения. Проверьте, разрешено ли **чтение журнала/записей** для целевого филиала. Важно: точное название разрешения для конкретного API-метода `records.list` официальной статьёй не подтверждено; если нельзя однозначно связать видимое право с методом — `APP_RECORDS_READ=unknown`. Ничего не включайте автоматически; увеличение прав требует отдельного решения владельца, только минимально необходимое чтение. Успех других методов, наличие partner-токена и код `15` не доказывают доступ к записям. Не копируйте и не отправляйте токен.

5. **Доступ к API по тарифу/подключению.** В доверенном интерфейсе филиала проверьте, что API/интеграция для чтения записей действительно включена по действующим условиям. Обычное наличие платной лицензии YCLIENTS **не доказывает конкретный API-доступ**. Если контракт/опция не показывает этот уровень детализации, укажите `API_ACCESS=unknown` и запросите у поддержки YCLIENTS подтверждение для филиала без передачи секретов/клиентских данных.

6. **Зафиксируйте только пять категорий ниже.** Не прикладывайте скриншоты, ID, ссылку на приватный филиал, raw API-ответ или данные пользователей. При `no` ничего не исправляйте в рамках этой задачи: отдельно согласовывается право минимального чтения и повторная проверка.

## Безопасный формат ответа

Скопируйте только строки, заменив `unknown` на подтвержденное значение:

```text
BRANCH_MATCH=unknown
SYSTEM_USER_IN_BRANCH=unknown
JOURNAL_SCOPE=unknown
APP_RECORDS_READ=unknown
API_ACCESS=unknown
```

| Поле | Допустимые значения | Что проясняет |
| --- | --- | --- |
| `BRANCH_MATCH` | `yes/no/unknown` | Совпадение целевого `company_id` с нужным филиалом |
| `SYSTEM_USER_IN_BRANCH` | `yes/no/unknown` | Действующая роль учетной записи в этом филиале |
| `JOURNAL_SCOPE` | `all/own/none/unknown` | Возможность видеть нужный журнал и масштаб видимости |
| `APP_RECORDS_READ` | `yes/no/unknown` | Подтверждено ли приложению чтение записей |
| `API_ACCESS` | `yes/no/unknown` | Подтверждено ли API-подключение/условие доступа |

**Интерпретация:** значение `no` у филиала, членства, scope приложения или API-доступа — конкретное направление для владельца; `none` у журнала означает отсутствие UI-доступа; `own`/частичный доступ требует проверки применимости к задаче синхронизации **всего филиала**. Но ни одно поле в одиночку не доказывает первопричину серверного `records.list → 403`: возможны отличающиеся ограничения API и UI, состояние токена, формат запроса или ограничения периода. Любой `unknown` оставляет соответствующую гипотезу открытой.

## Следующий этап — отдельно разрешаемый

После пяти UI-результатов координатор сверяет ограничения и сообщает владельцу, что именно подтверждено. **Только владелец**, после отдельного решения об очередной живой read-only пробе и соблюдения [`docs/SPIKE_RUNBOOK.md`](../SPIKE_RUNBOOK.md), может запустить контролируемый `records.list` probe. Агент его **не запускает**, даже если файл секретов существует. Допустимый общий диагностический результат — ограниченная фиксированная категория (`http_403` / `http_403_code_15`), не тело `403`, не сообщение или HTTP-заголовки. Код `15` не устанавливает конкретное отсутствующее право.

**Issue #37 остаётся BLOCKED; T-104 не разблокирована.** Любое изменение `docs/API_MATRIX.yaml` с `pending` на `verified` требует отдельно подтверждённых схемы/семантики/полноты и независимого QA, а не только UI-проверки или HTTP 200.

**Ограничение:** публичные UI-руководства YCLIENTS объясняют, где назначаются права системному пользователю приложения, но **не доказывают**, что конкретное приложение подключено к нужному филиалу, имеет разрешение на `records.list` и поддерживается тарифом. Эти факты проверяет владелец в приватном интерфейсе/договоре или через поддержку без передачи секретов.

# T-201 — отчёт исполнителя для независимого [R]

Задача: GitHub Issue #6. База: `0376ae4b04ab0b5dbf5814c5194506e22cb11182`
(origin/main, merge PR #4 / T-105). Отдельный worktree `tg-bot-t201`,
ветка `t-201-rbac`. Это отчёт исполнителя, не независимый вердикт.

## Реализовано

- Чистый default-deny `can()`, action matrix в CONTRACTS; неизвестные,
  непривязанные и отозванные пользователи не получают бизнес-привилегий.
- Bootstrap строго OWNER_TELEGRAM_ID с закреплением ID в kv; повторный запуск
  и два конкурентных старта идемпотентны. Другой ID не повышается.
- Приглашения admin только от owner, teacher от admin/owner. Срок преподавателя
  строго 24 часа. В invites только хеш; outbox хранит nonce. HMAC с внешним
  ключом Telegram позволяет восстановить ссылку исключительно при доставке.
- Атомарное одноразовое погашение, проверка актуальных прав создателя,
  запрет самовыдачи/повторного использования. Teacher остаётся без
  teacher_kind и доступа к занятиям до T-401/T-301.
- Отзыв отдельным флагом access_revoked, отмена pending/summary, проверка
  отзыва перед будущими отправками. Миграция сохраняет существующих users.
- Все изменения и аудит в одной транзакции; повторные запросы не дублируют
  эффекты. Команды и polling интегрированы, Telegram только через outbox.
- Ошибки не отражают введённые токены в сообщения/логи. Автор — from_user.id
  в личном чате; ID из команды не может подменить автора.

## Проверки

`make setup`: PASS. `make check`: PASS (461 тест).
Ruff format/check, pyright: без ошибок и предупреждений.

Независимому ревьюеру обязательно повторить `make check` по REVIEW.md.
Матрица: 350 комбинаций action × субъект × цель, неизвестные actions,
отозванные субъекты. Интеграционные проверки: bootstrap/restart/race;
выдача/истечение/подмена/replay приглашений; два конкурентных redeem и issue;
отзыв vs старая команда; откат при сбое аудита для каждого write-сервиса;
подмена Telegram ID/чат/бот; отсутствие токена во всех таблицах, файле БД
и логах, включая неожиданный сбой; startup и shutdown polling.
Регрессии T-101/T-105 выполняются без изменений их критериев.

## Ограничения и передача

- Только синтетические данные, сеть запрещена тестовым сторожем. Секреты,
  реальные Telegram/YCLIENTS и deploy не использовались. API adapter T-102
  не изменён и не интегрирован из PR #3.
- Приглашение является bearer-ссылкой без заранее заданного получателя:
  первый допустимый пользователь получает роль. Не пересылать посторонним.
- Ротация секрета бота требует повторной выдачи ещё не доставленных ссылок.
  Уже доставленные ссылки проверяются по сохранённому хешу до их срока.
- Восстановление отозванного доступа и смена владельца вне T-201;
  сохранённые/новые приглашения не восстанавливают отозванного пользователя.
- Авторизация бизнес-сценариев T-203/T-301/T-401 вводится в своих задачах.
  Эти сценарии и YCLIENTS-привязка не реализованы заранее.
- Ограничение доставки Telegram после remote acceptance до commit из T-105
  остаётся: exactly-once на стороне Telegram не обещается.
- Декомпозиция T-201a–e указана в PLAN; каждый коммит меньше ~400 строк.
  Полный diff для ревью: `git diff 0376ae4..HEAD`.

Следующее действие — независимое [R], затем решение владельца по merge.
После принятия T-201 доступны T-203 и T-301; здесь они не начинаются.

## A. Диагноз блокера `records.list` (HTTP 403)

### A.1. Что фактически отправляет код (проверено по коду, без вызова)

Единственный кандидат (`app/integrations/yclients_guards.py`, `SAFE_READ_ROUTES["records.list"]`):

```
GET /api/v1/records/{company_id}?start_date={from}&end_date={to}&page={page}&count={count}
```

Трассировка `app/integrations/yclients.py::_route` + `scripts/spike_readonly.py::run_spike`:

- `company_id` подставляется из настроек; как сегмент пути он проходит проверку «положительное десятичное ASCII» (`_route`, строки 133–137). `from/to/page/count` — это query-поля, они **не** проходят числовую проверку (корректно: даты не числа).
- `run_spike` для `records.list` задаёт `from = to = сегодня (UTC).date().isoformat()` → `YYYY-MM-DD`, `page = 1`, `count = matrix.meta.page_size` (сейчас `200`).
- Значения URL-кодируются (`quote(..., safe="")`); для даты `2026-01-01` и чисел это no-op. Редиректы запрещены (`follow_redirects=False`), прокси из окружения игнорируются (`trust_env=False`).
- Заголовок авторизации формируется из `headers_candidates`: `Authorization: Bearer {partner_token}, User {user_token}` (`docs/API_MATRIX.yaml::meta`).

По исходникам адаптер **конструирует** GET к журналу записей с двумя компонентами заголовка; локальных ошибок формирования URL в этой трассировке не обнаружено. Это не подтверждает реальную доставку или валидность токенов и не объясняет боевой 403.

### A.2. Имена пути и параметров подтверждены документацией/обёртками (а не 403)

- Официальный [YCLIENTS API Blueprint, раздел «Коллекция записей»](https://yclientsru.docs.apiary.io/api-description-document) описывает `GET /records/{company_id}`, `page`, `count`, `start_date` и `end_date`; в примере запроса показаны `Bearer` и `User`. Это документальная форма интерфейса, не результат проверки конкретного аккаунта.
- Прямые реализации в сторонних SDK: [slowprog — `getRecords()`, строки 1021–1077](https://github.com/slowprog/yclients-api/blob/master/src/Yclients/YclientsApi.php#L1021-L1077) и [andrey-tech — `getRecords()`, строки 1109–1165](https://github.com/andrey-tech/yclients-api-php/blob/master/src/Yclients/YclientsApi.php#L1109-L1165). Они подтверждают историческое использование user-токена и имён параметров, но не гарантируют текущее поведение сервера.
- Дополнительные ключи `staff_id`, `client_id`, `c_start_date`, `c_end_date`, `changed_after`, `changed_before` встречаются в обёртках; **для диагноза текущего запроса** существенны только фактически переданные `start_date/end_date/page/count`.

**Вывод по именам:** кандидат `records.list` синтаксически и по параметрам соответствует тому, как endpoint описан публичными источниками. `start_date/end_date` — верные ключи (не `startdate`, не `from/till`; `from/till` — это ключи `activities.search`, и он `ok`). Это делает ошибки авторизации и прав наиболее вероятными причинами 403; однако первопричина не доказана без анализа тела ответа сервера и проверки владельцем (см. A.5–A.6).

### A.3. Что в YCLIENTS означает 403 (документировано) и почему вывод spike его не различает

**Установленные документами факты:**

- В [официальном API Blueprint](https://yclientsru.docs.apiary.io/api-description-document) встречается код ошибки **`15 ACCESS_FORBIDDEN`**, описываемый как недостаточность прав приложения **в приведённых там разделах**. Само наличие этого кода в справочнике не доказывает, что именно он возвращён `records.list` и что его причина исключительно partner-scope.
- [Справка YCLIENTS «Доступ к API»](https://support.yclients.ru/67-68-199--dostup-k-api/) описывает системного пользователя, выдачу user-токена и необходимость назначить ему права для добавления в филиал.
- [«Права доступа к журналу записи»](https://support.yclients.ru/284--prava-dostupa-k-zhurnalu-zapisi) описывает ограничения видимости записей и сотрудников на уровне интерфейса и ролей. Она **не гарантирует** определённого HTTP-кода или JSON-тела для любого такого ограничения.

**Неподтверждённые гипотезы:** строка «Необходима авторизация» может сопровождать ошибку аутентификации, но **не обнаружена в проверенном официальном API Blueprint** и не устанавливает конкретно неисправность user-токена. Аналогично предположение «нет доступа к журналу/филиалу → код 15» **не подтверждено** схемой ответа `records.list`. Ни один из вариантов тела в нашем spike не наблюдался.

**Ключевое ограничение диагностики:** spike по дизайну печатает только категорию статуса. `_request_json` на не-2xx вызывает `raise AdapterError(status_code=status)` и **отбрасывает тело**; `AdapterError` хранит лишь `status_code` (`yclients_policy.py`). `_categorize` возвращает `"http_403"` без кода/сообщения YCLIENTS. **Поэтому по текущему выводу spike причины 403 неразличимы.** Изучение возможного кода ошибки допустимо только при отдельном разрешении владельца и безопасной классификации по A.6: даже текст ошибки может содержать PII. Также необходимы проверки доступа владельцем в интерфейсе.

### A.4. Сигнал из общей картины результатов (гипотеза, не факт)

Наблюдаемый паттерн:

- `ok`: `company.get` (`/company/{id}`), `services.list` (`/company/{id}/services/`), `activities.search` (`/activity/{id}/search`), `staff.list` кандидат 1 (`/staff/{id}`).
- `403`: `staff.list` кандидат 0 (`/company/{id}/staff/`), `records.list` (`/records/{id}`).

**По одному лишь распределению `ok`/403 нельзя разделить методы на partner-only и требующие user-токен.** В частности, успешный `activities.search` нельзя считать публичным или partner-only: [официальный API Blueprint, «Поиск групповых событий», `GET /activity/{company_id}/search`](https://yclientsru.docs.apiary.io/api-description-document) показывает в примере **оба** сегмента авторизации — `Bearer` и `User`.

Наблюдаемый паттерн допускает разные гипотезы: неполные права системного пользователя для журнала, недействительность или неверную область действия токена, несоответствие филиала, scope приложения, параметры запроса либо иные ограничения. Успех `activities.search` **не доказывает** валидность user-токена; но и не поддерживает утверждение, что успешно прошли исключительно partner-only методы. Тело ответа 403 неизвестно, связь «конкретный endpoint → конкретная причина» не установлена (A.3).

### A.5. Ранжированные причины 403 → безопасная проверка

Номера — **порядок практической проверки**, а не измеренные вероятности причин. Каждая гипотеза привязана к синтетическому тесту либо к ручной проверке владельца (без токенов и новых вызовов).

| # | Гипотеза причины 403 | Статус | Как проверить безопасно |
| --- | --- | --- | --- |
| 1 | У пользователя user-токена нет доступа к **журналу записей** в его роли в этом филиале | гипотеза (приоритет) | Владелец: UI-чек-лист A.6, п. 2–3. Безопасного автотеста нет — это внешнее право. |
| 2 | user-токен невалиден/просрочен/не доставлен либо не действует для нужной операции | **гипотеза**, не выведенная из успешных методов | Владелец проверяет настройку и привязку системного пользователя без раскрытия токена; отдельно разрешённая безопасная классификация HTTP-ошибки (A.6) может уточнить направление. Тест T1 в B.1 проверяет только локальное формирование заголовка. |
| 3 | Аккаунт user-токена не привязан как сотрудник/админ к **этому** `company_id` (филиалу) | гипотеза | Владелец: UI-чек-лист A.6, п. 1. `company_scope_bound=true` в отчёте означает лишь успех `company.get`, **не** совпадение филиала. |
| 4 | Приложению (partner) может не хватать права на метод записей (scope) | **гипотеза**; код 15 сам по себе не доказывает конкретную причину для records.list | Владелец сверяет выданные приложению права в партнёрском кабинете; сведения из справочника кодов не заменяют конкретное тело ответа и проверку прав. |
| 5 | Ограничение тарифа/доступа компании к API журналу | гипотеза (низкий приоритет) | Владелец: проверить тариф/подключение API у филиала; документального подтверждения в открытых источниках нет. |
| 6 | Неверный маршрут/параметры/версия endpoint | маловероятно: путь и параметры совпадают с публичными источниками (A.1–A.2); не доказано без тела ответа сервера | Для регрессии — предложенный синтетический тест T2 (B.1). |
| 7 | Некорректный период (`start_date==end_date` и т.п.) | не исключено без тела HTTP-ответа; 400/422 возможны, но не гарантированы | Синтетический тест T3 (B.1) проверит только обработку смоделированного 422, а не поведение сервера YCLIENTS. |

**Вывод A:** путь и параметры кандидата соответствуют публичным источникам (A.1–A.2). Проверка авторизации и прав (гипотезы 1–4) является первым практическим шагом диагностики 403, однако **первопричина не доказана**: анализ тела ответа сервера и проверка владельцем (A.6) обязательны до любых выводов о причине. Документального подтверждения альтернативного read-only endpoint, снимающего 403, **нет** → по Issue #38 A.4 **код и маршруты не меняются**. Спекулятивные `pending`-маршруты не добавляются.

### A.6. Чек-лист владельца в UI YCLIENTS (без токенов, без новых вызовов API)

Выполнить до любого повторного spike; это решение владельца.

1. **Филиал.** Убедиться, что `company_id`, под которым идёт spike, — это именно нужный филиал, и что пользователь системного user-токена **числится сотрудником/админом этого филиала** (Настройки → Сотрудники / Права доступа).
2. **Право на журнал.** В роли этого пользователя включено право видеть **«Журнал записей» / список записей** (а не только онлайн-запись). Проверить объём: все сотрудники или только свои.
3. **Область сотрудников.** Если роль ограничена «только своими записями», журнал по филиалу может отдавать 403/пусто — зафиксировать ограничение.
4. **Приложение-интеграция.** В партнёрском кабинете у приложения включены права на методы записей; «все права API» в одном месте не гарантируют выданный scope на конкретный метод.
5. **Тело 403 (однократно, безопасно).** При следующем отдельно разрешённом владельцем запуске получить только **диагностическую категорию**, а не полное тело ответа. Если YCLIENTS возвращает структуру `{"success":false,"meta":{},"data":{"code":N,"message":"..."}}`, поля находятся по путям `data.code` и `data.message` (не `error.code`/`error.message`). Схему необходимо подтвердить для конкретного 403, не считать её универсальной. Для журнала/отчёта допускаются только числовой `data.code` и заранее одобренная фиксированная категория сообщения (по точному белому списку известных строк); произвольный текст `message` **не выводить даже в обрезанном виде**, он потенциально содержит персональные данные или секреты. При неожиданной схеме/сообщении — только `http_403_unknown`. Полное тело и заголовки не логировать. Даже распознанный код/категория не является доказательством единственной причины; её устанавливают проверками владельца.
6. **Тариф/подключение.** Проверить, что у филиала активно API-подключение/тариф, дающий доступ к журналу.

Опциональный безопасный диагностический апгрейд (**не реализовано здесь; отдельное решение владельца и [R]**): извлекать только типизированный числовой код ошибки и безопасную категорию сообщения на основе **белого списка точных известных сообщений**; не сохранять и не выводить произвольный raw `message`, даже если он усечён до 200 символов. При неизвестных значениях возвращать `http_403_unknown` без деталей. Проверить respx-тестами на случайные PII/токены в `message`, необычную схему ответа и отсутствие утечки через исключения или логи. Это не даёт разрешения на live-вызов.

### B.1. Предложенные синтетические тесты T1–T3

> **Статус:** это предложения (proposals), **не** реализованные и не выполненные тесты. Используются только фиктивные токены и respx, без реального YCLIENTS API. Для реализации — отдельная задача и независимый [R].

**T1 — заголовок авторизации и обработка 403**

- **Входные условия:** сконструировать адаптер с фиктивными partner/user токенами и штатным шаблоном `Authorization: Bearer {partner_token}, User {user_token}`; respx отвечает `403` на точный маршрут `records.list`. Отдельный негативный вариант — тестовая матрица с намеренно неполным шаблоном заголовка, где есть только `Bearer`.
- **Ожидаемое поведение:** в штатном варианте перехваченный запрос содержит оба сегмента заголовка; `run_spike` записывает `http_403`, без retry. В негативном варианте зафиксировать фактическое поведение адаптера (сейчас отдельной проверки обязательности сегмента `User` нет); **не** считать его доказательством корректной авторизации.
- **Что доказывает:** формирование заголовка по матрице и реакцию текущего адаптера на смоделированный 403.
- **Что не доказывает:** пригодность или права реального user-токена и причину боевого 403.

**T2 — контракт пути и защита allowlist**

- **Входные условия:** respx перехватывает точный разрешённый URL `GET /api/v1/records/{company_id}` с `start_date/end_date/page/count`; адаптер вызывается с фиктивными значениями, мок возвращает 403. Отдельный негативный вариант — `ApiMatrix` с изменённым/неразрешённым шаблоном маршрута.
- **Ожидаемое поведение:** в штатном варианте метод, путь и query совпадают с ожидаемыми и обрабатывается смоделированный 403. Для изменённого шаблона `safe_read_route()`/`ApiMatrix.resolve()` выдаёт `OperationDenied` **до сети**, а не HTTP 404.
- **Что доказывает:** локальный контракт маршрута и блокировку неразрешённых шаблонов.
- **Что не доказывает:** принятие сервером YCLIENTS этого URL или права аккаунта.

**T3 — обработка смоделированного 422 при ошибочном периоде**

- **Входные условия:** обратиться напрямую к `YclientsClient.request("records.list", values=...)` с фиктивным `start_date > end_date` и остальными обязательными параметрами; respx возвращает 422. Не использовать неизменённый `run_spike`, поскольку он задаёт равные даты.
- **Ожидаемое поведение:** адаптер поднимает `AdapterError(status_code=422)`; `_categorize` при отдельном вызове возвращает точное значение `http_422`, а не несуществующее `http_other`.
- **Что доказывает:** исключительно транспортную обработку **смоделированного** HTTP 422.
- **Что не доказывает:** какой статус реальный YCLIENTS возвращает на неверный период и чем обусловлен фактический 403.

## C. Замечания по безопасности и измерению (без незапрошенных правок)

1. **Бюджет запросов ≠ физический HTTP-cap.** `MAX_REQUESTS=50` и `requests_made` в отчёте считают **вызовы кандидатов**. Адаптер при `retry_backoff_seconds=[1,2,4]` делает **до 4 физических транспортных попыток на кандидат** (1 исходная + 3 повтора) при HTTP `429`, `5xx` **и `httpx.TransportError` (включая тайм-ауты)**. Полученный **403 не ретраится** (`_request_json`: не-429 и не-5xx → немедленный `AdapterError`), поэтому один 403-кандидат = ровно 1 физический запрос. Не утверждать «жёсткий физический потолок 50 HTTP».
2. **`--no-confirm`.** Пропускает интерактивное подтверждение фразой; для реального авторизованного запуска владельцем **не использовать** (он нужен только для неинтерактивных тестов).
3. **`page_size=None → count=0`.** `run_spike`: `page_size = matrix.meta.page_size or 0`; при `None` в `count` уйдёт `0`, что может само по себе дать отказ/пустоту в диагностике. Сейчас в `API_MATRIX.yaml` `page_size: 200`, проблема не актуальна — отмечено как наблюдение, **переписывание не вносится**.
4. **`company_scope_bound`.** В отчёте он = успех `company.get`, а **не** доказательство совпадения филиала.

## Итог и следующий шаг

- **Диагноз `records.list` 403:** путь и параметры кандидата соответствуют публичным источникам (A.1–A.2); авторизация и права (гипотезы 1–4 из A.5) — первый приоритет для проверки, но доказательств ранжирования вероятности нет. **Первопричина не доказана** без проверки владельцем (UI-чек-лист A.6) и безопасной классификации серверной ошибки (A.6, п. 5); вывод сырого тела ответа запрещён.
- **Правок кода/маршрутов/`API_MATRIX` нет:** документального альтернативного read-only endpoint, снимающего 403, не найдено (Issue #38 A.4 → оставить без изменений).
- **До действий владельца:** выполнить UI-чек-лист A.6; при следующем отдельно разрешённом spike зафиксировать только числовой код и безопасную категорию ошибки 403 (A.6).
- **T-103 остаётся открытой, T-104 заблокирована** до подтверждённого базового `records.list` и независимой проверки обезличенных доказательств. Повторный spike, изменение прав в YCLIENTS и любой live-тест — отдельное решение владельца.

# AUTONOMY — поэтапный переход к автономной разработке

**Текущее фактическое состояние:** **нет** ни Runner, ни диспетчера. Не утверждать обратное до ревью и проверки кода. Эта документация описывает целевой процесс.

## Фаза A: сейчас, без диспетчера

1. Владелец клонирует репозиторий и запускает Claude Code в локальном терминале.
2. Claude Code берёт T-101, создаёт ветку `t-101-...`, пишет тесты и код, выполняет `make check` после появления Makefile.
3. Исполнитель фиксирует коммит и отчёт, но не делает push/merge/deploy.
4. Владелец передаёт код/diff координатору на ревью; последующий шаг определяют статусы и зависимости `PLAN.md`.
5. T-001 готовит владелец отдельно. Реальный YCLIENTS `make spike` выполняет только владелец.

## Фаза B: T-106 Runner

- Локально запускает одну заданную задачу через CLI Claude Code.
- Фиксирует `task_id`, ветку, `base_sha`, `head_sha`, session ID, статус, attempts.
- Независимо выполняет `make check`, не доверяя выводу агента.
- Состояние атомарно и с блокировкой одного запуска; после прерывания не удваивает побочные эффекты.
- На провале останавливается; никакого автоматического merge/deploy.

## Фаза C: T-107 GPT-ревью

- Только для `[R]` и ревью этапа; задача без `[R]` не получает фиктивный APPROVE.
- Отправляет полный проверенный diff и критерии, предварительно проверяет безопасность.
- Verdict: `APPROVE` или `REQUEST_CHANGES`, при недоступности доказательств/API — `BLOCKED`.
- Ревью привязано к SHA: новый SHA всегда требует новых проверок.
- При замечаниях Runner передаёт точечный промпт обратно Claude Code.
- Ограничение повторов, затем эскалация человеку.

## Фаза D: T-108 диспетчер

- Читает граф зависимостей `PLAN.md`, не придумывает задачи.
- Ведёт очередь `PENDING -> READY -> RUNNING -> CHECKING -> REVIEW -> APPROVED/CHANGES_REQUIRED/BLOCKED`.
- Работа в отдельных git worktree, одного task_id не берут два агента (lease).
- Параллелизм только для задач с закрытыми зависимостями и непересекающимися файлами.
- Не продолжает автоматически при конфликте веток, отсутствии тестов, незнакомом API, риске данных, изменении ADR или исчерпании попыток.
- Нет автоматического merge, deploy, публикации секретов и реальных API-вызовов.

## Разделение ответственности

Владелец утверждает ADR, реальный запуск YCLIENTS, merge и deploy. Координатор проводит ревью, эскалацию и план. Исполнители пишут тесты и код. Любое утверждение о готовности должно иметь commit SHA, результаты проверок и независимое ревью по правилам.

## Очерёдность разработки

Сейчас T-101 и T-001 параллельно. После T-101 возможны T-102, T-105 и T-106 (в независимых ветках/worktree). До приёмки T-107 GPT-ревью остаётся ручным; до приёмки T-108 диспетчера нет. Не блокировать продуктовую разработку ожиданием оркестратора.
